### 加工の流れ

1. ZIPは原本として保持し、選抜したglTFと依存するbin・画像を C:/Users/rukat/manmarubuu-travel/assets/source/ 配下へ取り出す。FBX/OBJを同時に複製しない。
2. glTFの実寸、軸、床の高さ、ピボットを調べ、まんまるぶうのゲーム内高さ1.65mを基準に建物や小物の寸法を揃える。
3. 建築プレハブ、簡易コライダー、木と主な小物のLODを生成する。開閉する扉・宝箱は固定メッシュに結合しない。
4. 不透明部分と葉のマスク部分を分ける。原版のdoubleSidedやalphaModeを全素材へ無条件で引き継がず、形状と画像の透明度に応じて扱う。
5. 環境モデルはGLB＋外部共有テクスチャを基本にし、同じ壁材やトリムを各モデルへ重複内包しない。材質・画像は読み込みキャッシュを共有する。
6. 配信用のテクスチャはKTX2、形状は必要に応じMeshoptで圧縮する。変換ツールの導入が詰まった場合は選抜GLB＋適切に縮小した画像で先に通し版を成立させ、圧縮のために物語の実装を止めない。
7. C:/Users/rukat/manmarubuu-travel/public/assets/ に実行時に使うものだけ出す。各素材の元パス、作者、ライセンス、変換条件、三角形数、材質数、サイズをmanifestへ記録する。

影の境目、苔、汚れ、木材の濃淡は素材と配置に持たせる。作り込む近景と簡略化する遠景を分け、木と小物には一貫した風・色・光の方向を与える。元のSource版シェーダーを必要としない、WebGL2用の小さな表現で構成する。

## 4. まんまるぶうの書き出しを変更する

モデルの加工元は戦闘モーション入りblend。読み込み時はスクリプト自動実行をOFFにし、元blendへ保存しない。派生作業ファイルは C:/Users/rukat/manmarubuu-travel/assets/working/characters/ に置く。

| 部分 | 加工方法 |
| --- | --- |
| 胴・頭・手足 | 部位別の簡略化。頬、鼻、耳の縁、接地部の輪郭を保つ |
| 布 | 元の色とプロシージャルな粒度をUVへ焼き付ける。照明の影は色へ重ね焼きせず、AO等と分ける |
| 毛 | 大量のCurvesそのものの出力を避け、ループの陰影を法線・粗さへ。輪郭に短い毛カードと少量のループ形状 |
| 目 | 閉じた刺繍形状を専用に再構成し、顔の表面位置へ合わせる。遠距離用の色・法線にも同形状を残す |
| 縫い目 | 顔と輪郭の重要部分は形状、細部はベイク。元と同じ色・方向 |
| 材質 | 布部分にsheenを使う。目と鼻の材質には汎用のノイズbumpを一律適用しない |
| アニメーション | 13クリップ、ボーン階層、部品の追従を保持。歩行の原点移動と戦闘ルート移動を二重に適用しない |

LOD0は本体60,000～90,000三角形＋近接毛10,000～20,000を初期予算、LOD1は25,000～40,000、LOD2は10,000～15,000を目安にする。これは目標であり、未生成の成果物の実測値ではない。元モデル全体を単に低ポリゴンへ置き換える目的ではなく、今より少ない形状で顔と布の情報を増やす。

LODは主役の画面内サイズで選び、切り替えに余裕幅を持たせる。顔の重要形状を一緒に消さない。最高・高の近接毛は目の周囲へ生やさず、スキニング／親ボーンの変形へ追従させる。毛カードの影は近距離に限定し、遠方で不安定な細い影を描かない。

sheenは布の光の返りを表すもので、毛の輪郭を自動で作る機能ではない。環境光と専用の毛表現を組み合わせる。[Three.js MeshPhysicalMaterial](https://threejs.org/docs/pages/MeshPhysicalMaterial.html) でもsheenと追加コストを確認しており、使用は主役と近い主要NPCへ絞る。

## 6. 進行状態とイベント契約

正本は永続milestonesの集合とし、章段階、扉の開閉、NPC会話、紋章の所持はそこから導出する。別々の「現在の章番号」とフラグを両方書き換えて同期させる方式を避ける。

| 受け付けるイベント | 前提 | 一度だけ確定する状態 |
| --- | --- | --- |
| DISAPPEARANCE_HEARD | 新しい旅 | abductionKnown |
| REQUEST_ACCEPTED | abductionKnown | requestAccepted |
| TOWER_ACTIVATED | requestAccepted＋回転盤正解 | towerActivated |
| CAVE_BOSS_DEFEATED | towerActivated＋戦闘勝利 | caveBossDefeated。紋章所持を導出 |
| CREST_RESTORED | caveBossDefeated＋台座操作 | crestRestored。紋章所持を解除 |
| ALTAR_LIT | crestRestored＋遺跡の経路成立＋祭壇操作 | altarLit |
| SHRINE_ENTERED | 三つの封印条件が成立 | shrineEntered |
| SHRINE_BOSS_DEFEATED | shrineEntered＋主との戦闘勝利 | shrineBossDefeated |
| LILY_RESCUED | shrineBossDefeated＋救出会話終了 | lilyRescued |
| HOMECOMING_COMPLETED | lilyRescued＋再会イベント終了 | homecomingCompleted |

gateOpen = towerActivated AND crestRestored AND altarLit。chapterClear = homecomingCompleted。紋章所持 = caveBossDefeated AND NOT crestRestored。リリィの同行 = lilyRescued AND NOT homecomingCompleted。この導出により「持ち物を失ったが扉は開かない」などの矛盾を避ける。

仕掛けの途中状態は別に保存する。塔は三つの0～3の向き。遺跡は水門A/Bの状態と開通した近道。演出再生済みID、宝箱ID、ボス以外の配置の復帰情報も必要な分だけ保存する。

物語イベントは同じIDを再送しても報酬や進行を重複確定しない。前提不足の操作には、その場所の短い説明を返す。未来のイベントを飛ばして解除する入力は受け付けない。

## 7. エリア、歩行、読み込み

エリアIDは village、forest、tower、cave、ruins、shrine-court、shrine-upper、shrine-lower、shrine-core。6つの建物の室内は村の同一座標内に構成し、戦闘舞台だけ別途生成する。エリア定義にasset参照、配置、歩行面、コライダー、portals、出現点、調べる場所、照明、環境音を持たせる。

探索地形の高さを一つのheightAt(x,z)だけで決めない。塔の上下階、洞窟、橋とその下は、現在の階層と支持面を持つ歩行面として扱う。階段には傾斜の支持面を置き、床の切れ目や天井との衝突も定義する。

プレイヤーは簡易カプセル、壁は単純な箱・向き付きの箱・必要部分だけの地形衝突。近傍検索は空間グリッドで絞る。建築の細かなポリゴンや草の一枚ごとに物理を付けない。各入口には復帰可能なsafeSpawnを明記する。

同時に保持する世界は「現在のエリア＋次の一エリア＋主役と共通UI」が基本。境界へ近づいたら次を先読みし、家は開閉する扉を通って暗転なしで歩いて入る。地下と地域間は短い暗転で切り替える。読み込みの失敗は再試行でき、進行や旧エリアを失わない。glTFの参照を捨てるだけでなく、不要になったGPUリソースも共有参照を確認して解放する。

リリィの追従はまんまるぶうの通った安全な経路を記録して後追いする方式を基本にする。壁越しに直線追尾させない。階段・portalでも追従し、詰まった場合は画面外の安全な同行位置へ復帰する。救出後の帰還先は常に二人分確保する。

## 8. 戦闘とイベントの時間軸

現行のawaitと固定時間待機の列を、update(dt)で進む中断可能な行動シーケンスへ移す。データはactionId、actor、target、duration、animation、path、cameraShots、events、endPoseを基本とする。

戦闘計算は描画から独立させる。コマンド検証→行動順確定→各行動の開始時に結果計画を作成→命中時に結果を一度反映、の順で処理する。片方が倒れたら後続行動を計画しない。MP・道具消費、ダメージ、報酬はイベントごとの一意IDで二重適用を防ぐ。

行動後は戦闘舞台の6～8個の安全な立ち位置から次の位置を選ぶ。実際の経路は直線または短いBezier曲線とし、接触間隔・攻撃方向・足場内の収まりを保証する。主役と敵の大きさから接近距離を決め、全敵へ同じ距離を使わない。

カメラの所有者は一つとし、探索追従が戦闘の寄りを毎フレーム上書きしない。カメラの経路にも壁・天井の確認を行い、予定の画が使えない場合は安全な引きの画へ戻る。シェイクは基準姿勢からの一時オフセットにし、加算し続けて位置をずらさない。

スキップや高速再生で命中を飛び越えたときは、通過したイベントを一度ずつ適用する。アプリの非表示中は演出時間を休止し、復帰時の巨大なdtで技が壊れないようにする。全てのエフェクトはプールを利用し、粒子の使い捨て生成とGPUリソースの放置を避ける。

物語のカットシーンも同じ時間軸の基本機能を使う。モーリとリリィの抱擁は二人の基準位置・向き・手の到達点を揃えた専用クリップを作り、終了後の立ち位置まで定義する。中断後は保存済みの直前の区切りから再開する。

## 9. 描画品質と予算

WebGL2のWebGLRendererを継続する。現在あるThree.jsのGLTFLoader、AnimationMixer、LOD、InstancedMesh、描画パスを使う。WebGPU専用化、レイトレーシング、新しい大型物理エンジンを今回の前提にしない。

静的な建物・道・室内にはベイクした陰影と環境光、動く人物には近距離の影を使う。昼の主光源は一つ、室内の影付き補助光は画面の見せ場に絞る。ランタンや炎は発光材質と小さな局所光を使い分け、全てに高価な影を付けない。

最高・高はRenderPass→半解像度GTAO→控えめなBloom→SMAA→OutputPassを基準にする。標準はAOを省き、軽量はFXAAと簡単な出力だけにする。パスの有無が変わっても露出と色空間を揃える。主役を白飛びさせるブルーム、戦闘を読めなくする深い被写界深度は初期設定に入れない。

色テクスチャと発光テクスチャはsRGB、法線・粗さ・AOは非色データ。最終出力の色変換を二重に適用しない。[Three.js Color Management](https://threejs.org/manual/pages/color-management.html) に沿ってGLTFLoaderとOutputPassの役割を保つ。

描画のまとめ方は、同じ形状・材質の繰り返しをInstancedMesh、少数しか使わない静的建築部品を局所的な結合とする。草木は約24～32m単位のセルへ分け、遠いセルをまとめて除外できるようにする。世界全体を一つの巨大なバッチにしない。葉の風は深度・影にも同じ変形を適用し、影だけ静止しないようにする。

| 指標 | 最高 | 高 | 標準 | 軽量 |
| --- | --- | --- | --- | --- |
| 主描画の可視三角形 | ～150万 | ～100万 | ～60万 | ～30万 |
| 主描画のdraw call | ～450 | ～350 | ～220 | ～140 |
| 参照中のテクスチャ容量の推定予算 | ～768MiB | ～512MiB | ～256MiB | ～160MiB |
| 短い効果音の同時発音数 | 24 | 24 | 16 | 12 |

全て初期の制作予算であり、fps保証や合格を自動判定する絶対値ではない。影・AO等の追加パスのコストは別に計測する。ブラウザからVRAM使用量を正確に取得できる前提を置かず、解像度・形式・mipmap・配列数から容量を推定する。

解像度倍率は表示領域の物理ピクセルに対する倍率とする。高DPIで無意識に負荷を増やさないよう、初期の描画上限を2560×1440相当とし、カスタムから変更できる。UIは内部解像度を下げても画面の解像度で描く。品質を変更したらrendererとcomposerのサイズ、影、AO、エフェクト設定を同時に更新する。

テクスチャ品質は別サイズのファイルを用意する。最高用画像をGPUへ保持したまま表示だけ小さくして「軽量」と呼ばない。変更は探索中なら適用し、戦闘中はモデル・テクスチャの差し替えだけ行動終了後へ予約する。設定値と進行は保持する。

初期読み込みは主役・村・導入の素材を優先し、祠最深部やボスを同時に待たせない。配信サイズは主役と最初のエリアで圧縮後25～40MiB、追加エリアは各10～25MiB程度を目安にする。使用素材の選抜前の設計予算であり、ビルド実測値とは区別する。

ゲーム画面の任意のFPS表示には現在のプリセットと内部解像度も表示する。一般ノートの具体的なGPUは未指定のため、端末が決まるまでは達成済みとしない。ヘッドレスのスモークテストのfpsをRTX 4060やノートPCの性能証明に使わない。

KTX2は圧縮したままGPU向けの形式へ変換する用途、Meshoptは形状データの圧縮用途として扱う。GLTFLoaderへ必要なデコーダーを設定し、ファイルはローカル配信する。[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)、[KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)、[InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html)、[LOD](https://threejs.org/docs/pages/LOD.html) を参照した。

新キーは manmarubuu.sealed-shrine.v2 とし、旧キー manmarubuu.three.adventure.v1 は残す。旧世界の座標、種、番人撃破を新しい章へ移行しない。settingsだけは値域を検証して互換なものを移せる。

## 11. 音源実装

指定フォルダの原本を、このプロジェクトの C:/Users/rukat/manmarubuu-travel/assets/source/audio-library/ へコピーし、元と同じファイル名・クレジットを保持する。原本を読み取るコードを本番ゲームに入れず、使用する音だけ C:/Users/rukat/manmarubuu-travel/public/audio/ へ配置する。公開するソースの範囲が後で決まった場合も、素材集の単体配布とゲーム組み込みを区別する。

BGMと長い環境音は必要な曲だけ読み、短いSFXは共有AudioBufferで再生する。全ての長尺MP3を同時にデコードしてメモリへ常駐させない。ループの開始・終了、音量、空白は実装時に音源ごとに決める。

音量バスをMaster/BGM/SFX/Ambienceに分ける。足音は移動距離と接地タイミング、命中音は戦闘イベント、扉音は可動部の開始と停止に同期させる。方向と距離のある環境音を適用し、同じ足音を毎フレーム重ねない。

全40本について長さ、平均音量、ピーク、参考LUFSを計測済み。結果は [音源の長さ・音量レポート](C:/Users/rukat/manmarubuu-travel/docs/audio-level-audit.md) に記す。音源の品質はユーザー判断を採用し、試聴や曲選びのやり直しは行わない。調整対象は再生する長さとゲインだけとし、元音源を変更しない。
